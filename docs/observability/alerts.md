# Alerts

Alert rules as PromQL for any Prometheus (ADR-0012). Every failure mode has a rule here or a
written decision to defer it. Metrics are computed from Postgres ledgers at scrape time; until
they land, the deferred entries below say what watches the failure meanwhile.

| Failure mode | Signal | Status |
|---|---|---|
| The dispatcher stops (Beat or the broker down) | no `dispatch.completed` log for 15 min; later the age of the newest scheduled scan | Deferred to the P1 `queue-backlog` and `redis-unavailable` runbooks. Meanwhile the beat container's healthcheck watches its schedule file. |
| A job can't be enqueued after commit | `job.enqueue_failed` (warning) | Deferred to `redis-unavailable` (P1). The scan stays queued and the sweep sends it again within 5 min, so nothing is lost. |
| A brand is never scanned (bad schedule or settings) | `dispatch.brand_rejected` (warning, with the error class) | Deferred: a per-brand error belongs on the brand's settings page, which will show it; it is not an on-call page. |
| A "Scan now" can't be built from a brand's stored settings | `scan_now.rejected` (warning, with the error class) | Deferred, like `dispatch.brand_rejected`: the brand page tells the owner the settings can't be used, and the settings page fixes them; not an on-call page. |
| A scan runs past its time limit | `scan.timed_out` (warning); failed scans with reason `timed_out` | Covered by the P0 `scan-failures-high` alert when scan metrics land. |
| Labelling or grouping stops early (the model down or refusing) | `labelling.stopped`, `grouping.stopped` (warning); `llm_calls` rows with outcome `failed` | Covered by the P0 `llm-errors-high` alert when LLM metrics land. The texts stay pending, and the mentions wait for a story; the next scan picks them up. |
| Grouping runs out of time (labelling took most of the scan) | `grouping.out_of_time` (warning); scans finished `partial` with `enrichment_failed` | Deferred: the waiting mentions go to the next scan that labels something new; the scans dashboard shows it with `scan.timed_out`. |
| The model's grouping answer is partly unusable (unknown ids, a missing placement, a story too long) | `grouping.placements_dropped` (warning, with counts and the call id) | Deferred: a prompt-quality signal for the eval, not an outage; the mentions keep waiting. |
| An alert can't be explained (the model down, refusing, out of budget or misconfigured; a lost nudge) | `explanation.failed` (warning, with the error class); `explanation.refused` (warning: the answer carried a link, contact details or invisible characters, so it isn't stored or emailed); `job.enqueue_failed` with `job=explain_alert`; alerts with no `alert_explanations` row after 10 minutes (dashboards.md) | Covered by the P0 `llm-errors-high` alert when LLM metrics land; no alert of its own: the alert, its notification and its email stand without the explanation, which only adds words (ADR-0008). Runbook: `llm-errors-high` (P1). |
| A draft can't be written (the model down, refusing, out of budget or misconfigured, or in replay mode one the recordings don't hold; it cited a mention it wasn't shown, or carried invisible characters) | `draft.failed` (warning, with the error class); `draft.uncited`, `draft.refused` (warning, with the call id) | Deferred: a person asked and sees the failure on the page with a retry (ADR-0008); `llm-errors-high` covers a model that is down. `draft.uncited` is a quality signal for the prompt's eval, not an outage. |
| A user's monthly LLM budget runs out | `llm_budget.exhausted` | Deferred to the P1 `llm-budget-exhausted` runbook. Scans go on without labels, and the usage page will show the spend. |
| The day's model spend across all users reaches `LLM_DAILY_GLOBAL_CAP_MICROS` | `llm_budget.global_exhausted` (warning) | Deferred to the P1 `llm-budget-exhausted` runbook with the per-user budget: every model call stops until midnight UTC, so scans go on without labels and drafts fail with the page's retry. A cap reached most days means it is set too low, or someone is abusing open sign-up (ADR-0015). |
| A surface stops short in a scan (SerpApi failing, a circuit open, a budget spent) | `surface.stopped` (info, with surface, outcome and code); `scan_surface_results` rows not `succeeded` | Covered by the P0 `serpapi-errors-high` alert when SerpApi metrics land; the scan finishes `partial` and the overview shows which surface was missed. |
| A scan runs out of time mid-collection | surface outcome `failed` with code `scan.deadline_passed` | Covered by the P0 `scan-failures-high` alert with the scan's other failures; no search starts past the deadline, so nothing more is billed. |
| A scan stage raises (a database error, a bad settings snapshot, a scoring defect) | `scan.stage_failed` (error, with the error class); scans finished `failed` with reason `stage_failed` | Covered by the P0 `scan-failures-high` alert when scan metrics land. |
| A failed scan can't even be finished (the database down) | `scan.finish_failed` (error) | Covered by `scan-failures-high` through the sweep, which times the scan out within its limit; `postgres-unavailable` (P1) for the cause. |
| A finish arrives after the sweep timed the scan out | `scan.finish_lost` (warning) | Deferred: a sign the time limit is too tight, not an outage; reviewed on the scans dashboard with `scan.timed_out`. |
| A scan is skipped for a spent search budget | scans finished `skipped` with reason `budget_exhausted` | Deferred to the P1 `serpapi-quota-low` runbook; the user sees the skip in the app (#96 adds the notification). |
| Labelling or grouping can't run (settings the model rejects, a missing prompt) | `labelling.misconfigured`, `grouping.misconfigured` (error); scans finished `partial` with `enrichment_failed` | Covered by the P0 `llm-errors-high` alert; a deploy error, so it pages rather than waiting for the next release. |
| A user's saved model settings no longer validate (a model since dropped from the allowed list) | `llm_profile.invalid` (warning, with the user id and which tasks were dropped) | Deferred: calls fall back to the preset for those tasks alone, so nothing fails; it is a release-notes item when a model is retired, not an on-call page. |
| An email can't be sent yet (mail server down, a 4xx reply, credentials refused) | `outbox.send_failed` (warning, with the message id, kind and code); pending messages past due | Covered by the `outbox-backlog` runbook (its backlog query) until outbox metrics land; then alert when the oldest due pending email is over 5 minutes late. It backs off and is retried up to 8 times, about two hours, then is `dead`. |
| An email can never be sent (a 5xx reply, 8 retries, a message that can't be built or rendered) | `outbox.dead` (error, with the code); messages with status `dead` | Covered by the `outbox-backlog` runbook (its failures query) until outbox metrics land; then alert on any `dead` message in the last hour. |
| The rate limiter can't reach Redis (it lets sign-in requests through) | `rate_limit.unavailable` (warning) | Deferred to the P1 `redis-unavailable` runbook; meanwhile the global cap on issued codes (200 an hour, counted in Postgres) still bounds a flood. |
| Someone floods sign-in (one source, or many) | `otp.request_limited`, `otp.verify_limited` (warning, per source); `otp.global_limit` (warning, every address together) | Deferred to the P1 `otp-abuse` runbook: an abuse signal, not an outage; the limits already hold, and the answers reveal nothing. |
| Someone guesses the operator console's password (ADR-0014) | `admin.login_failed` (warning), `admin.login_limited` (warning); `audit_events` rows `admin.login_failed` (dashboards.md) | Deferred to the P1 `otp-abuse` runbook, with sign-in floods: the limits hold (5 per source per 15 minutes and 30 an hour overall in Redis; 30 failures an hour counted in Postgres, which holds when Redis is down) and a 16-character password outlasts them. A run of failures is the cue to change `ADMIN_PASSWORD`, which also ends every console session. |
| Replay mode has no recorded answer (a search the recordings don't hold, a model task they don't cover) | `serp_call.failed` with code `serpapi.http_4xx` (status 404) and `llm_calls` failed with `llm.replay_unrecorded`, in `SERPSENSE_MODE=replay` only | Decided not to alert: replay is a demo of recorded data, refused in production, and a gap is a missing piece of the built-in story (a test walks every scan for one), not an incident. The scan finishes `partial`, as a live scan with a failed surface would. |
